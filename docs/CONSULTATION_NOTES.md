# Voice-Recorded Consultation Notes

A clinician records a consultation with a patient; the audio is transcribed
in near-real-time by a self-hosted Whisper model, and the clinician writes
up a structured note (Chief Complaint / History of Present Illness /
Assessment / Plan) referencing the growing transcript. This doc covers the
whole pipeline — schema, endpoints, audio handling, and how to run/test it
locally. For the frontend half, see nexusApp's
`docs/linking-consultation-notes.md`.

## Why no AI-generated summary

The transcript is real (Whisper), but the SOAP note fields are typed by the
clinician, not generated by an LLM. This was a deliberate scope decision,
not a missing feature — auto-summarizing a clinical transcript needs an LLM
API call (cost, latency, and a new external dependency), and the priority
for this phase was getting real recording + real transcription working
end-to-end first. Revisit this once transcription quality/coverage is
proven out on real consultations.

## Data flow

```
Browser (MediaRecorder, ~10s chunks)
        │  POST /api/v1/consultation-notes/{id}/audio-chunk (multipart)
        ▼
Rust backend (src/handlers/consultation_notes.rs)
        │  saves chunk to disk, forwards bytes
        ▼
ml-service POST /transcribe (ml-service/voice.py)
        │  self-hosted faster-whisper — audio never leaves this infrastructure
        ▼
Rust backend appends the segment + running transcript to Postgres
        │
        ▼
Response carries the updated full_transcript → frontend appends it live
```

This is **chunked near-live transcription**, not true streaming ASR: the
transcript grows in ~10s steps as each chunk finishes, not word-by-word.
True streaming would need a websocket + incremental decoding on the
ml-service side — a materially bigger lift, and not needed yet.

## Schema (`migrations/20240062_create_consultation_notes.sql`)

- **`consultation_notes`** — one row per consultation. `status` is
  `recording` → `completed` (or `failed` if abandoned). `full_transcript`
  is the running concatenation of every segment's text. `chief_complaint`,
  `history_of_present_illness`, `assessment`, `plan` are clinician-authored,
  nullable until saved via `PATCH`.
- **`consultation_transcript_segments`** — one row per audio chunk:
  `audio_path` (where the chunk landed on local disk), `transcript_text`,
  `status` (`completed`/`failed` — a failed chunk doesn't fail the whole
  note), `last_error`.

Audio chunks are stored on local disk under `uploads/consultations/{note_id}/`
(configurable via `CONSULTATION_UPLOAD_DIR`), not object storage — this
matches the project's current maturity level (no S3/Cloudinary integration
exists anywhere else in this backend yet). Revisit if deployment moves to
multiple backend instances without shared disk.

## Endpoints

All role-gated to `HealthWorker`/`HospitalAdmin`, same as the rest of the
patients API.

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/patients/{patient_id}/consultation-notes` | Start a new note |
| `GET` | `/api/v1/patients/{patient_id}/consultation-notes` | List a patient's notes, newest first |
| `GET` | `/api/v1/consultation-notes/{id}` | Fetch a note + its transcript segments |
| `POST` | `/api/v1/consultation-notes/{id}/audio-chunk` | Upload + transcribe one audio chunk (multipart: `sequence`, `audio`) |
| `PATCH` | `/api/v1/consultation-notes/{id}` | Save structured fields (all optional — partial saves supported) |
| `POST` | `/api/v1/consultation-notes/{id}/complete` | Mark the note completed |

Full request/response shapes: Swagger at `/api/docs` (tag
`consultation-notes`), or `src/handlers/consultation_notes.rs` directly.

## ml-service: `/transcribe`

See `ml-service/README.md`'s "Voice transcription" section for the Whisper
model config (`WHISPER_MODEL_SIZE`/`WHISPER_DEVICE`/`WHISPER_COMPUTE_TYPE`)
and a known gotcha with HuggingFace's "xet" download backend.

## Running locally

```bash
cargo run   # auto-starts ml-service too — see README's Quick Start
```

The Whisper model downloads on the **first** `/transcribe` call (not at
ml-service startup), so the first recording in a fresh environment will be
slower while it downloads — subsequent ones are fast. `WHISPER_MODEL_SIZE=tiny`
is a good default if you're on a slow connection or want fast local
iteration; the shipped default is `base` for better accuracy.

## Verifying it end-to-end without a real microphone

Useful for testing without a browser:

```bash
TOKEN=<a real JWT for a hospital_admin or health_worker user>
PATIENT_ID=<an existing patient id>

# 1. Start a note
NOTE_ID=$(curl -s -X POST "http://localhost:8080/api/v1/patients/$PATIENT_ID/consultation-notes" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "import sys,json;print(json.load(sys.stdin)['id'])")

# 2. Upload a chunk (any short audio file works — webm/opus is what the
#    browser actually sends, but any format ffmpeg/faster-whisper can
#    decode works for testing)
curl -X POST "http://localhost:8080/api/v1/consultation-notes/$NOTE_ID/audio-chunk" \
  -H "Authorization: Bearer $TOKEN" \
  -F "sequence=0" \
  -F "audio=@/path/to/clip.webm;type=audio/webm"

# 3. Complete it
curl -X POST "http://localhost:8080/api/v1/consultation-notes/$NOTE_ID/complete" \
  -H "Authorization: Bearer $TOKEN"
```

## Known limitations

- No speaker diarization — the transcript is a flat feed, not separated
  into "doctor said" / "patient said" turns (the frontend's now-deleted
  mock UI faked this; the real implementation doesn't claim it).
- No AI-generated note summary (see above).
- Audio stored on local disk, not object storage — see Schema section.
- Near-live, not true streaming transcription — see Data flow section.
